設計書を分割して個別のMarkdownファイルにするという判断は、LLMのコンテキスト管理において非常に賢明な選択です。

各ファイルが「LLMにとって読みやすく、かつ人間にとっても誤解のない状態」であるかを検証するための**レビューチェックリスト**を、ファイルの役割ごとに提案します。

---

### 0. 全ファイル共通：黄金律（Golden Rules）
どのファイルに対しても、まず以下の3点を確認してください。

- [ ] **一意のID化:** すべての要求事項や決定事項に `REQ-001` や `ADR-001` のような一意のIDが付与されているか？
- [ ] **単一責任の原則:** そのファイルは、一つのトピック（例：あるコンポーネントの要件のみ）に集中しているか？（肥大化して複数の役割を持っていないか）
- [ ] **リンクの整合性:** `[[title]]` 形式による内部リンクが正しく機能し、LLMが「辿れる」ようになっているか？

---

### 1. 要求事項系ファイル
(`Allocated Requirements.md`, `Derived Requirements.md`)

要求事項は、実装とテストの「正解」となるため、最も厳密さが求められます。

| チェック項目 | 確認内容 | LLMへの影響 |
| :--- | :--- | :--- |
| **原子性 (Atomicity)** | 1つのIDに対して、要求事項が1つだけに絞られているか？（「〜して、かつ〜する」はNG） | 実装・テストコード生成時の漏れを防ぐ |
| **検証可能性 (Testability)** | 「適切に」「速やかに」などの曖昧な表現を避け、数値や状態の変化で判定できるか？ | テストケースの自動生成精度が上がる |
| **トレーサビリティ** | 上位要求（Parent ID）への参照が含まれているか？ | 影響範囲の分析（Impact Analysis）が可能になる |

---

### 2. アーキテクチャ設計ファイル
(`Architecture Overview`, `Structure`, `Behavior`)

これらはシステムの「構造」と「動き」を定義します。

| チェック項目 | 確認内容 | LLMへの影響 |
| :--- | :--- | :--- |
| **図解のコード化** | 複雑な関係性は、テキストではなく Mermaid.js 等で記述されているか？ | 図に基づいたロジック生成が可能になる |
| **役割の明確化** | 各コンポーネントの「責任（何をするか）」と「境界（何をしないか）」が定義されているか？ | コンポーネント間の責務の重複を防ぐ |
| **データフローの明示** | データの入力 $\rightarrow$ 加工 $\rightarrow$ 出力 の流れが、インターフェースを通じて記述されているか？ | シーケンス図や実装コードとの整合性が高まる |

---

### 3. ADR (Architecture Decision Records) ファイル

意思決定の「なぜ（Why）」を記録する重要なファイルです。

| チェック項目 | 確認内容 | LLMへの影響 |
| :--- | :--- | :--- |
| **コンテキストの記述** | 「何が問題だったのか」「どのような制約があったのか」が具体的に書かれているか？ | 類似の設計変更を依頼された際の判断基準になる |
| **代替案の検討 (Alternatives)** | なぜ他の選択肢ではなく、この決定に至ったのかが明記されているか？ | LLMによる「もっと良い方法はないか？」という提案への回答になる |
| **帰結 (Consequences) の記述** | この決定によって生じるトレードオフ（メリットとデメリット）が書かれているか？ | 設計の妥当性をLLMに検証させる際に不可欠 |

---

### 4. サブコンポーネント要件ファイル
(`Sub-component Requirements.md` ※各コンポーネントごと)

実装に最も近い、具体的な設計図です。

| チェック項目 | 確認内容 | LLMへの影響 |
| :--- | :--- | :--- |
| **インターフェースの厳密性** | OpenAPI形式や型定義など、機械的に解釈可能な形式で記述されているか？ | コード生成（ボイラープレート作成）の精度が劇的に上がる |
| **制約事項 (Constraints)** | 使用すべきライブラリ、メモリ制限、タイムアウト値などが明記されているか？ | 実装時の「勝手な判断」によるバグを防ぐ |
| **依存関係の明示** | どのコンポーネントに依存しているか（またはされていないか）が明確か？ | モック作成やユニットテスト生成の指示が容易になる |

---

### 💡 Tips: LLMを「レビュアー」として使う方法

これらのチェックリストを作成したら、LLM自身にレビューを行わせるプロンプトを用意しておくと非常に効率的です。

**プロンプト例:**
> 「あなたはシニア・ソフトウェアアーキテクトです。これから提示する `Sub-component Requirements.md` を、以下の【レビューチェックリスト】に基づいてレビューしてください。
> 
> 【レビューチェックリスト】
> - [ここに上記の表の内容を貼り付け]
> 
> 不足している点や、LLMが実装を行う際に曖昧になりそうな箇所があれば、具体的に指摘してください。」

このように、**「人間が定義した基準」を「LLMに適用させる」**というサイクルを作ることで、設計書の品質を自動的に高めていくことができます。

## Operational Guidelines

### Preparation

プロジェクトごとに、以下のルールを準備する。

1. ID付与ルール・記法、参照の記法と、トレーサビリティ完全性のチェック方法
2. インターフェース定義の記法・フォーマット
3. 必要に応じて、状態遷移テーブルのフォーマット

### How to design

本テンプレートを用いたアーキテクチャ設計は、人間とLLMの協調を前提に、以下のステップで段階的に進めます。

1. **要求の集約 (Requirements)**: 上流文書から要求を抽出し、IDを付与してリスト化する（LLMに抽出とID割り振りを支援させる）。
2. **アーキテクチャ方針の決定 (ADR)**: 技術的なトレードオフが発生する箇所について、ADRを作成して方針を決定する（人間が決定し、LLMにADRのドラフトを作成させる）。
3. **構造と技術要求の定義 (Architecture)**: 決定した方針に基づき、サブコンポーネントの分割（Structure）と技術要求（Technical Requirements）を定義する。
4. **ユースケース分析 (Use Case Analysis)**: 主要なユースケースごとにシーケンス図（Mermaid）を描き、サブコンポーネント間のインターフェース要求を導出する。
5. **サブコンポーネント要求の集約 (Sub-component Requirements)**: 各ユースケースから導出された要求を、サブコンポーネントごとにMECEに整理・統合する（LLMによる重複排除と構造化が極めて有効なフェーズ）。
### Verification

設計書の品質を担保するため、以下のチェックリストを用いて検証（人間によるレビュー、またはLLMへのプロンプトによる自動検証）を行います。

- [ ] **トレーサビリティの完全性**: `Sub-component Requirements` にあるすべての要求IDが、`Use Case Analysis` または `Technical Requirements` のいずれかのIDを導出元として参照しているか？
- [ ] **孤立した要求の排除**: `Requirements` に定義された要求のうち、どの `Technical Requirements` や `Use Case` にも紐付いていない「孤立した要求」が存在しないか？
- [ ] **ADRの整合性**: `Architectural Decisions` で決定された事項が、`Technical Requirements` や `Structure` に正しく反映されているか？
- [ ] **MECE（モレなくダブりなく）**: 複数のユースケースで登場する類似のインターフェース要求が、`Sub-component Requirements` で適切に共通化・整理されているか？
- [ ] **構文の妥当性**: すべての Mermaid 図や構造化データ（OpenAPI等）が、シンタックスエラーなくレンダリング可能か？
